# Задачи для домашней работы

## Задача 1. Отображение детальной информации заказа при наведении

У нас новый заказ! Нам необходимо начать делать интернет-магазин, и любой интернет-магазин начинается с каталога.

Интерфейсы со множеством карточек часто требуют показа дополнительной информации при наведении курсора. Чтобы не вешать обработчики на каждую карточку, предлагаем использовать **делегирование событий**.

В этой задаче нужно реализовать функцию `setupOrderHandlers`, которая как раз и будет отображать подробную информацию о товаре.

### Цели задачи
- Научиться использовать **делегирование событий**.
- Понять **всплытие событий**.
- Реализовать **динамическое отображение информации** по заказам при наведении.
- Скрывать информацию при уходе курсора.

### Общая спецификация поведения

1. Каждый заказ - это элемент с классом `order`.
2. У заказа есть уникальный `id`, имя клиента, список товаров, общая сумма, адрес и статус, которые хранятся в атрибутах `data-*` на самом заказе.
3. При наведении (`mouseover`) на заказ:
    - отображается дополнительная информация: `client`, `items`, `total`, `address`;
    - стиль карточки меняется (например, тень, увеличение масштаба).
4. При уходе курсора (`mouseout`):
    - детальная информация скрывается;
    - стиль возвращается к исходному.
5. Обработчик событий должен быть **только на родительском элементе** (делегирование).
6. Чтобы экономить ресурсы, после первого наведения информация не должна удаляться из DOM, а скрываться (`opacity: 0` и `height: 0`).
7. Код должен корректно работать при **динамическом добавлении** новых заказов.

### HTML-структура

Структуру из файла `index.html` можно использовать для отладки.

### Примеры состояния заказа до и после

Запуск функции.

```js
setupOrderHandlers(document.getElementById('orders'));
```

Что должно происходить:

**До наведения**
```html
<div class="order" data-id="1" data-client="Иван Иванов" data-items="Бургер, Картошка фри" data-total="420 ₽" data-address="ул. Пушкина, д. 10" data-status="new">
  Заказ #1 - Новый
</div>
```

**После наведения**
```html
<div class="order" data-id="1" data-client="Иван Иванов" data-items="Бургер, Картошка фри" data-total="420 ₽" data-address="ул. Пушкина, д. 10" data-status="new">
  Заказ #1 - Новый
  <div class="order-details">
    <strong>Клиент:</strong> Иван Иванов<br>
    <strong>Товары:</strong> Бургер, Картошка фри<br>
    <strong>Сумма:</strong> 420 ₽<br>
    <strong>Адрес:</strong> ул. Пушкина, д. 10
  </div>
</div>
```

## Задача 2. Поиск и фильтрация заказов по статусу

Заказчик доволен карточками заказов, но теперь хочет иметь возможность **искать заказы** по номеру заказа, заголовку или имени клиента и **фильтровать** их по статусу.

Такая задача очень часто встречается на сайтах и приложениях, поэтому нам точно нужно попробовать её реализовать.

В этой задаче нужно реализовать функцию `setupOrderSearchHandler`, которая подключает обработчики к поиску и фильтрам и фильтрует заказы в реальном времени.

### Цели задачи
- Научиться работать с событиями ввода.
- Реализовать **поиск по нескольким полям заказа** и **фильтрацию по статусу**.
- Искать заказы в реальном времени при вводе клиентов в поисковую строку.
- Добавить кнопку - очистку поиска для удобства клиентов.

### Общая спецификация

1. В HTML есть:
    - `<input type="text" id="order-search">` - поле поиска;
    - `<span class="search-clear">✕</span>` - кнопка очистки;
    - `.filter-ready`, `.filter-new` - чекбоксы фильтрации;
    - `<div id="orders">` - контейнер с заказами.
2. Каждый заказ:
    - имеет класс `order`;
    - имеет атрибуты: `data-id`, `data-status`;
    - имеет `.order-title` и `.order-client` - для поиска;
    - по умолчанию видим.
3. При вводе текста в поиске:
    - заказы фильтруются, если **в `data-id`, `.order-title` или `.order-client`** встречается **подстрока** из поиска;
    - фильтрация происходит сразу же после введения каждого символа;
    - поиск **без учёта регистра**;
    - заказы, не прошедшие фильтр, скрываются (`display: none`).
4. При клике на крестик:
    - поле поиска очищается;
    - применяется повторная фильтрация.
5. При изменении чекбоксов:
    - показываются только заказы с соответствующими `data-status`;
    - «Готовые» - `cooking`, `delivery`, `delivered`;
    - «Новые» - `new`;
    - если оба чекбокса **выключены** - показывать **все**.
6. И поиск, и фильтры применяются одновременно (логическое AND).
7. Функция должна корректно работать с **уже существующими** и **динамически добавленными** заказами.

### HTML-структура

Структуру из файла `index.html` можно использовать для отладки.

### Пример

Запуск функции.

```js

    document.getElementById('order-search'),       // Поле ввода поиска
    document.querySelector('.search-clear'),       // Кнопка-крестик для очистки поиска
    document.querySelector('.filter-ready'),       // Чекбокс «Готовые» (cooking, delivery, delivered)
    document.querySelector('.filter-new'),         // Чекбокс «Новые» (new)
    document.getElementById('orders')              // Контейнер с заказами
);
```

| Действие                             | Что должно произойти                                             |
|--------------------------------------|------------------------------------------------------------------|
| Ввод текста в поиске                 | Заказы фильтруются по `data-id`, `.order-title`, `.order-client` |
| Клик по крестику                     | Поле поиска очищается, фильтрация сбрасывается                   |
| Клик по чекбоксам                    | Фильтрация по статусу обновляется                                |
| Добавление нового заказа в `#orders` | Он участвует в фильтрации                                        |

## Задача 3. Поиск заказов с задержкой и загрузкой с сервера

Заказчик доволен поиском и фильтрацией, но хочет, чтобы поиск происходил **с задержкой** и **загружался с сервера**. Потому что он увидел, что так реализовано на других сайтах.

Вообще, это очень распространённая практика, когда поиск происходит не сразу, а с задержкой, чтобы не нагружать сервер и не делать лишних запросов. 

А отправка запросов на бэк необходима, когда данных слишком много и высылать их все на фронтенд бывает слишком долго.

В этой задаче нужно реализовать функцию `setupOrderSearchServerHandler`, которая подключает обработчики к поиску и фильтрует данные, полученные сервера, в реальном времени.

### Цели задачи
- Научиться реализовывать **debounce** через `setTimeout` / `clearTimeout`.
- Научиться **загружать данные асинхронно** при поиске в реальном времени.
- Следует **обрабатывать ошибки** и показывать их пользователю, для улучшения UX.
- Явно **отрисовывать список заказов при загрузке страницы**.

### Общая спецификация

1. В HTML есть:
    - `<input type="text" id="order-search">` - поле поиска;
    - `<span class="search-clear">✕</span>` - кнопка очистки поиска;
    - `<div id="orders">` - контейнер с заказами;
    - `<div id="search-error" class="error-message"></div>` - блок для вывода ошибок.
2. Каждый заказ:
    - имеет класс `order`;
    - имеет атрибут `data-id`;
    - имеет класс статуса (`new`, `cooking`, `delivery`, `delivered`);
    - содержит `.order-title` и `.order-comment`.
3. При вводе текста в поиске:
    - запускается debounce-таймер в **300 мс**;
    - по истечении таймера:
        - выполняется запрос к `searchOrdersOnServer(searchText)` с текущим текстом в поиске;
        - если поиск пустой - загружаются все заказы.
4. Поиск должен происходить аналогично по тем же полям (`data-id`, `.order-title`, `.order-comment`).
5. При клике на крестик:
    - поле поиска очищается;
    - загружаются все заказы с сервера.
6. В случае ошибки:
    - показывается сообщение внутри `orders` с текстом ошибки `«Ошибка при загрузке заказов»`.
7. В случае отсутствия результата:
   - показывается сообщение внутри `orders` с текстом `«Ничего не найдено»`.
8. При загрузке страницы:
    - должны загрузиться и отобразиться **все заказы** с сервера.
9. Функция должна корректно работать с **динамически добавленными заказами**.
10. Используй `async` и `await` для ожидания данных от поиска.

## Задача 4. Кнопка «Избранное» 

> Обрати внимание, что на эта задача не проверяется автотестами, так как требует подключения визуальных эффектов и их оценки. Комментарии к этой задаче ты можешь получить в рамках код-ревью.

На любом сайте заказов есть кнопка, которая позволяет добавлять товар в «Избранные».

Заказчик хочет, чтобы карточки заказов позволяли **отмечать избранные**, но и ещё сделать различные состояния у неё при нажатии (визуальные эффекты).

### Цели задачи
- Научиться работать с **состояниями элемента**.
- Реализовать **анимацию вращения** через `requestAnimationFrame`.
- Научиться **останавливать анимацию**.
- Не забыть учесть, что на кнопку могут нажимать множество раз и всё должно работать корректно.

### Общая спецификация
1. Каждый заказ - элемент с классом `order`.
2. В каждом заказе должна быть кнопка «Избранное»:
   ```html

   ```
3. У кнопки три состояния:
   - **не выбрано**: серое сердце;

   - 3-й клик: удаляются оба класса, анимация останавливается.
5. Анимация:
   - бесконечное вращение вокруг оси на 360°;
   - плавное, через `requestAnimationFrame`;
   - останавливается при повторном клике на кнопку и переходит в состояние серого сердца.
6. Реализовать через **делегирование событий** (один обработчик на `container`).

### Extra 1. Загрузка данных по кнопке и отображение в DOM

#### Что должно получиться

На странице есть кнопка «Загрузить» (или аналог) и контейнер для контента. По клику запускается «запрос» за данными. Пока данные грузятся, в контейнере показывается состояние загрузки (текст «Загрузка...», спиннер или затемнение). После успешного ответа в контейнер рендерится список или карточки. Если произошла ошибка - в контейнере показывается сообщение об ошибке. Повторный клик по кнопке во время загрузки не должен запускать второй запрос (нет «гонки»).

Нужно также написать функцию **`simulateRequest()`**, которая эмулирует запрос к нестабильному серверу: возвращает **Promise**, внутри которого через **`setTimeout`** с **случайной задержкой** (например, от 300 до 1500 мс) имитируется ответ. Исход запроса сделать **случайным** с помощью **`Math.random()`**: с вероятностью около 70% вызывать **`resolve`** с данными (например, массив карточек/заголовков), с вероятностью около 30% - **`reject`** с ошибкой (например, строка «Ошибка сервера»). Эту функцию использовать для «запроса» по кнопке.

#### Ограничения
- Только ванильный JavaScript. Запрос эмулируется функцией `simulateRequest()` по условию выше.

#### С чего начать

Функция `simulateRequest()` может выглядеть так (идея: случайная задержка и случайный исход):

```js
function simulateRequest() {
  return new Promise((resolve, reject) => {
    const delay = 300 + Math.random() * 1200;
    setTimeout(() => {
      if (Math.random() < 0.7) resolve([/* данные, например массив карточек */]);
      else reject('Ошибка сервера');
    }, delay);
  });
}
```

В основном коде: кнопка и контейнер в HTML; по клику проверяй флаг загрузки, ставь флаг и показывай «Загрузка...», вызывай `simulateRequest()`, в `then`/`catch` обновляй контейнер и сбрасывай флаг.

#### Подсказки

- **Промисы:** `new Promise((resolve, reject) => { ... })`, `then`, `catch`, `finally`. **async/await:** объяви функцию `async`, внутри `await` промиса; ошибки - `try/catch`.
- Состояние «идёт загрузка»: переменная-флаг; в начале клика проверяй её, по завершении запроса сбрасывай.
- Обновление DOM: очисти контейнер (`innerHTML = ''` или `replaceChildren()`), создай элементы из данных и добавь в контейнер.

**Примечание.** Если хочешь попробовать реальный запрос к API - можно дополнительно сделать вариант с **`fetch`** к публичному API, например [PokéAPI](https://pokeapi.co) (список покемонов и т.п.).

### Extra 2. Несколько асинхронных источников (Promise.all и ошибки)

#### Что должно получиться

На странице есть кнопка «Загрузить всё» и контейнер. По клику нужно «запросить» данные из **двух или трёх «источников»** одновременно. Когда все источники успешно ответили - показать в контейнере объединённый результат (например, три блока или один общий список). Если хотя бы один источник вернул ошибку - показать пользователю сообщение об ошибке и при желании отобразить то, что успело загрузиться. Двойной клик во время загрузки не должен запускать вторую порцию запросов.

Нужно написать для **каждого из 2–3 источников** свою функцию-заглушку (например, `simulateSource1()`, `simulateSource2()`), которая возвращает **Promise** с **`setTimeout`**. Задержку в `setTimeout` сделай **случайной** через **`Math.random()`** (например, каждый раз от 200 до 2000 мс), чтобы источники «отвечали» в разное время. Исход (resolve/reject) тоже можно сделать случайным или фиксированным - на твоё усмотрение, главное чтобы иногда один из источников мог «падать», чтобы проверять обработку ошибок.

#### Ограничения
- Только ванильный JavaScript. Источники эмулируются функциями, возвращающими Promise с `setTimeout` и случайной задержкой.

#### С чего начать

Заглушки для источников могут выглядеть так (случайная задержка при каждом вызове):

```js
function simulateSource1() {
  return new Promise((resolve, reject) => {
    const delay = 200 + Math.random() * 1800;
    setTimeout(() => resolve(/* данные */), delay);
  });
}
// аналогично simulateSource2(), simulateSource3() - при желании с случайным reject
```

По клику вызывай **`Promise.all([simulateSource1(), simulateSource2(), ...])`**. В `then` - массив результатов, сформируй разметку и вставь в контейнер. В `catch` - покажи сообщение об ошибке. Флаг загрузки - чтобы блокировать повторный клик. Разберись, как ведёт себя `Promise.all` при первом же reject; при желании используй **`Promise.allSettled`**, чтобы отобразить успешные результаты и отдельно сообщение об ошибке по неуспешным.

#### Подсказки

- **`Promise.all(iterable)`** - ждёт все промисы; если все resolved - массив результатов; если хотя бы один rejected - сразу reject с этой ошибкой.
- **`Promise.allSettled(iterable)`** - ждёт все промисы и возвращает массив `{ status, value }` / `{ status, reason }`; по нему можно отобразить успешные и показать ошибку по неуспешным.
- Обработка ошибок: `.catch()` у цепочки или `try/catch` при `await Promise.all(...)`.

- HTML и JS и краткий комментарий в MRе: как обрабатываешь ситуацию, когда один из источников вернул ошибку (Promise.all vs allSettled или иначе).

### Extra 3. Промис с resolve и reject «снаружи»

#### Что должно получиться

На странице **три кнопки**: «Начать», «Успех», «Ошибка».

- При нажатии **«Начать»** - отображается индикатор загрузки (лоадер, текст «Загрузка...» или иная реализация).
- При нажатии **«Успех»** - показывается текст об успехе (например, «Успех» или «Данные загружены»).
- При нажатии **«Ошибка»** - показывается текст об ошибке (например, «Ошибка» или «Что-то пошло не так»).

Логика должна быть такой, что «завершение» (успех или ошибка) происходит именно по нажатию соответствующей кнопки, а не по таймеру. То есть пользователь нажимает «Начать», видит загрузку, затем сам решает - нажать «Успех» или «Ошибка», и в интерфейсе отображается соответствующий результат.

#### Ограничения
- Только ванильный JavaScript. Используй промис и события клика по кнопкам.

#### Подсказки

- **`resolve`** и **`reject`** можно использовать не только внутри конструктора промиса - их можно сохранить (например, в переменные) и вызвать позже из другого места, в том числе из обработчика события.
- Один и тот же промис переходит в состояние fulfilled или rejected только **один раз**; повторные вызовы `resolve`/`reject` игнорируются.
